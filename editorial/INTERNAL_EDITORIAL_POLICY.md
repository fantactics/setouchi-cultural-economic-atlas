# SETOUCHI ATLAS｜制作・公開の運用手順（第3層）
更新：2026年11月22日

**内部運用文書。** この文書は公開サイトの説明ページに掲載しません。公開GitHubリポジトリではMarkdown自体は閲覧可能なので、秘匿情報や未許諾素材は記録しません。

編集判断の優先順位は、[第1層：編集理念](../EDITORIAL_PRINCIPLES.md) → [第2層：文章・表現の指針](../EDITORIAL_WRITING_GUIDE.md) → **本書（制作・公開手順）**。本書は可変的な実務を扱い、理念を変更する権限を持ちません。

## 1. 変更を始めるとき

1. 作業対象をエッセイ／研究ノート／地域ページ／写真・タグ・検索／サイトレイアウトに分け、実際の公開URLと編集元ファイルを確認する。
2. 既存作品・現地写真・研究ノートの知見カードを確認し、同じ内容の重複を避ける。新しい作品の問いと既存作品の違いを明らかにする。
3. 調査を先に行い、必要なら追加資料を探す。現行仮説に都合のよい資料だけで結論を固めない。
4. 変更範囲は必要最小限にする。他の記事、ヘッダー、フッター、KII ATLASのビルド成果物を意図せず変えない。
5. **公開済み記事のslugとURLは原則維持**する。統合・移管が必要なときは、リンク・転送と検索・関連記事を合わせて更新する。

## 2. 原稿・出典・データの管理

- SETOUCHIには `src/content/essays/*.md` と `src/data/*.js` による**併存する記事データ**がある。編集前に、`src/pages/book/[slug].astro` が実際にどちらを採用しているか確認する。Markdownだけを修正して終わったと判断しない。
- 既存のタイトル・副題・導入・地域・タグ・写真・関連記事・出典メタデータの整合を確認する。CMSで編集するときは未表示フィールドが欠落していないか差分を見る（詳細は `docs/PAGES_CMS_MIGRATION.md`）。
- 核となる地形・自然現象・年代・数字・歴史的因果には一次資料を優先する。典拠が弱い場合は、事実／解釈／仮説の区別と未解決点を残す。現地で確認していない視覚情報を補わない。
- 公開エッセイは**読み物優先**。詳細な検証手順、比較表、未解決の調査課題は原稿データや研究ノートへ。末尾のナンバリングした参考文献リンクは維持し、参照先・番号の整合を確認する。
- 現存する企業の経営判断・取引関係・効用や、個人の心理・会話を、資料の裏付けなしに確定的に書かない。新しい研究結果と矛盾する既存記述は修正する。

## 3. 研究ノートの更新手順

公開ページは **「調査と研究ノート」 `/chapters/`**。次の記事の問いを発見するための知識庫であり、研究仮説の結論を強制する場所ではありません。

データ本体：`src/data/researchWritingNotebook.js`。新規エッセイの着手前に関連する知見カードを調べ、既存エッセイ・比較研究・一次資料へ進む。

**更新の判断**：調査で新しい事実、比較、説明の修正、未解決の問いが生じたら、該当カードを更新。既存カードに合わなければ新規に追加する。新しい知見がなければ更新しなくてよい。

| データ項目 | 更新する内容 |
| --- | --- |
| `title`, `question` | 風景の具体的な疑問。研究の分類名ではなく読者がわかる言葉 |
| `finding` | 今確認できる説明と、解釈である部分。一般法則に拡張しない |
| `next` | 次に一次資料・観察・比較で確かめたい問い |
| `use` | 次のエッセイで何を調べる手掛かりになるか |
| `essays`, `research`, `sources` | 根拠となる既存エッセイ、比較ノート、実在の資料リンク |
| `notebookUpdated` | 知見カードを実際に改訂した日付 |

1. 調査中の発見を、事実・解釈・仮説・未解決の問いに分ける。
2. `finding` と `next` を見直し、関連する作品と出典を参照できるようにする。**反証や例外があれば研究ノートの方を修正する。**
3. 同一分野の詳しい分析は専門研究ノートへ。公開トップの知見カードは、今後の執筆に使える焦点に絞る。
4. 初期の研究・専門評価手法は `notebookArchiveGroups` の書架へ保存し、全分野の共通原則にはしない。古いURLを削除・改名するときは転送と参照先を確認する。
5. エッセイと研究ノートを相互に照合し、知見の更新日、リンク、公開表示を確認する。

## 4. 写真・地図・視覚編集

- **主題と一致する写真を最優先。** 別地域・別製品・別時代の画像を実物写真として誤認させない。根拠に合う写真がない場合は、無理に代用品を置かない。
- 写真は装飾や枚数合わせではなく、風景の証拠と理解のために選ぶ。本文写真は控えめにし、必要があれば増やせる。従来の「4〜5節で1枚」「6節以上で2枚」は**目安であり上限や必須数ではない**。
- 自分で撮影した写真は本人素材として利用できるが、提供者や撮影場所の確認を省略しない。外部素材は利用許諾・ライセンスと必要な表示を確認し、内部の権利記録も残す。ユーザーが提供した画像の権利を自動的に一般公開素材とみなさない。
- 画像の代替テキスト、解像度、スマートフォン表示を確認する。アイキャッチと本文の内容が一致するか実際に表示して確かめる。
- 公開するエッセイの地図は実際の対象地を示す。同名地名や誤った市町村、施設位置の誤認に注意。海底地形・海岸線の変化には必要なら航空写真・海図・比較図を使う。
- 本文の強調・色・装飾は少なめにし、見やすさを優先する。「色付き強調は概ね3か所以内」も**運用上の目安**であり、説明の必要性とデザインを優先して判断する。

## 5. 分類・読者導線・検索

- 代表的なカテゴリは食文化／農業景観／港と船／海と島／歴史的町並み／都市景観／工業景観／観光景観。新たなテーマに応じて見直せる分類であり、調査理論ではない。
- 「地名から」「自然条件から」「文化・風習から」の役割を分ける。**自然条件タグ**は地質・地形・風・潮・水・気候・生態など、記事の内容に実際に関係する条件だけ。「晴天」と「日照」のような同義語を増やさない。信仰・交易・技術などは文化側で扱う。
- 写真、地名、自然条件、検索、関連記事からの入口を維持する。公開記事のタイトル・一覧カード・サイト内検索・SEOタイトル・description・OG・構造化データに旧題が残らないか確認する。
- 参考文献と外部リンクを確認し、古い研究ノートや公開ページを整理するときは404や検索上の孤立をつくらない。

## 6. 公開前後の確認（変更した範囲に応じて）

**公開前：** 事実・年代・因果と出典、読みやすさ、画像の対象地・権利、地図位置、タイトル・見出し、リンク、タグ、SEO、表示を点検する。毎回すべての手作業を繰り返すのではなく、変更内容に応じて重点を変える。

**技術検証：** `npm run build` の後に必要な既存チェックを実行する。主なものは `scripts/check-published-links.mjs`、`scripts/check-research-notebook.mjs`、`scripts/check-essay-seo.mjs`、`scripts/check-built-editorial.mjs`。編集文書の整合は `scripts/check-editorial-policy.mjs`。 GitHub ActionsではこれらとKII側の検証を実行する。

**公開後：** GitHub Actionsのbuild・deploy成功を確認してから、実際のサイトでエッセイの導入、写真、地図、リンク、スマートフォン表示を確認する。ビルド成功を公開成功と混同しない。URL変更を伴うときは新旧リンク、サイト内検索、サイトマップ、Google向けメタ情報を確認する。

## 7. 文書の管理責任と更新基準

- **理念の変更**：作品とサイトの使命を変える重要判断として第1層へ反映。
- **文章の判断基準の変更**：最近の作品から繰り返し学んだ改善を第2層へ反映。
- **運用手順の変更**：CMS・表示・タグ・写真管理・研究ノートの実装に合わせて本書だけ更新。
- 過去の議論や個別の試行結果は `docs/`・`editorial/CLUSTER_REVIEW.md` に保存し、**古いメモを現行の命令文書として使わない**。文書間に矛盾があれば上位層を優先する。

KII ATLASには `KII_EDITORIAL_GUIDE.md` という固有の補足があります。共通理念は共有しますが、KIIの公開システムや写真・出典の固有ルールをSETOUCHIへ機械的に移しません。


## SEO・AIO共通メタデータ（SETOUCHI / KII）

- 記事ページは共通の `src/data/articleMetadata.js` から Article JSON-LD を生成する。媒体名を publisher とし、本文の地域・自然条件・文化タグ・公開された参考文献を再利用する。媒体名を個人著者とみなさず、未確認の著者名や経歴は追記しない。
- 新規公開時は実際の初回公開日を確認して `datePublished`（YYYY-MM-DD）を設定する。実質的な改稿時には `dateModified` を更新する。過去の公開日が不明な原稿は空欄とし、ビルド日やGitコミット日を初回公開日として一律に設定しない。日付を指定した場合は本文ヘッダーにも表示する。
- 公開用の独自ドメインURLへの変換後に `scripts/check-aio-artifact.mjs` で canonical、OG URL、Article JSON-LD、サイトマップ、robots.txt を照合する。KIIは独立パッケージの検査と実サイトへの配信を区別する。
- 検索クローラーの現行許可を維持する。AI学習用クローラーを制限する場合は検索用途と分けて個別に判断する。AI検索に特別なマークアップは必須ではないため、本文の品質と出典の確認を優先する。

- 自然条件の総論は `src/data/natureTopics.js` に記録し、個別エッセイの比較・相違点を読者に説明する。本文にない因果を新たに断定せず、参照する公開記事と対応する文献IDを保持する。記事を非公開化する場合は総論とのリンクも同時に見直す。索引・総論・記事の相互リンクとサイトマップ収録は公開前に自動検査する。
